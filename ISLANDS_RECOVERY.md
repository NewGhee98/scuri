# Islands: manual recovery later

Status reviewed 20 September 2026: the prevention fixes and later library/editor features are deployed through PR #28, but no historical Islands recovery or fresh live project/Drive-original inspection is established by this documentation update. This manual procedure remains separate, requires explicit authorization and preserves originals and evidence. The current Project photos scrolling fix and document reconciliation do not change that boundary. See `PROJECT_CONTEXT.md` for release status.

This is a procedure for a later session with authorized live connectors. No live recovery, database inspection, Drive listing or deployment was performed for this code fix. Treat the handoff's project identifiers, counts, file listings and claims that originals survive as historical evidence to verify, not confirmed current state.

1. **Preserve evidence before opening the project in an app that can autosave.** Keep existing devices offline or close the unpatched app. Export the original device's `layouts.projects.v1` localStorage record, any legacy `layouts.current-project.v2`/`layouts.current-project.v1` records, and relevant blobs in IndexedDB `layouts-local-photos` / `photos` before reconnecting it. Do not clear caches or reinstall the app first.
2. **Verify identity and capture read-only live evidence.** Resolve the correct account and Islands project. Export its `projects`, `project_pages` and `project_assets` records and revision. Inventory the project's Drive folders, originals and previews with file ids, names, timestamps, size/checksum when available, and app properties. Keep duplicates and the damaged project intact. Check the actual deployed source version before permitting sync.
3. **Find authoritative historical placement data.** Inspect preserved device exports for page ids, frame ids, blob keys, Drive ids and crops. Also check whether a suitable database backup/PITR or prior export exists. Restore historical backups only into an isolated recovery environment for inspection; do not roll back the live database to recover this one project. The availability of such backups has not been established.
4. **If a complete mapping survives, prepare a reviewable restoration.** Validate every page/frame against the preserved templates, resolve blob keys to verified originals/previews, retain crops from evidence, and identify any ambiguity. Prefer a separate recovered project with fresh project/page/asset row ids while reusing verified original file references. If restoring the existing project is preferred, prepare an exact row-level diff and backup first, recheck its current revision, and obtain approval before the live write. Keep an auditable copy of the evidence either way.
5. **If no complete mapping survives, rebuild a separate `Islands (recovered)` copy manually.** Download or reference the verified originals, retain the surviving page templates, and let the user choose placements and crops. Do not assign images sequentially or assume every frame was filled. The reported number of files does not establish unique photos or historic placements. Use fresh database row identities; do not repurpose the original project's page/asset rows. This patch does not add a Drive recovery tray or automate the rebuild.
6. **Verify the recovered copy with the patched app.** Check the composition and crops with the user, then use a fresh browser/device: first without Drive connected, then after connecting. Confirm that metadata persists in both cases and photos load when their bytes become available. Only consider removing the damaged project or cleaning up duplicates as a separate, explicitly approved action.

New Drive app properties apply to future uploads only. They omit crop history and can become stale after rearrangement; they do not repair old files or replace Supabase as the source of truth. If historic assignment/crop records are gone, exact composition cannot be recovered with certainty from image files alone.
